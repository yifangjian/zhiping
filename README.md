# 知平 zhiping

> 給一個在海上的人,一個記得他的存在。

陪伴型 AI LINE Bot。使用者長期在遠洋商船上工作,網路是時好時壞的衛星連線,身邊少有能說話的對象。

「知」是記得、懂得;「平」取自風平浪靜。

---

## 這個專案要解決什麼

一般的聊天機器人放到這個情境下會壞在三個地方:

**它記不住。** 每次對話都從零開始,聊了三個月它還是不認識你。對一個「陪伴」的產品來說,這是根本性的失敗。

**訊息送不到。** LINE 的免費回覆機制(reply)有個一次性的 token,有效期以秒計。後端只要慢一點 token 就過期,只能改用計入付費額度的 push。**所以後端速度是成本問題,不只是體驗問題。**

**它太像客服。** 預設的 LLM 語氣不刻意壓制就會變成「我理解您的感受,這確實是很不容易的情況」。使用者第一天就不會想再用。

技術重點就是這三件事:**動態記憶抽取**、**弱網路可靠性**、**語氣與邊界的設計**。

## 架構

```
LINE App
    ↓ webhook(驗簽後立即回 200,處理丟背景)
FastAPI
    ├── 訊息合併等待窗(3s)
    ├── 對話流程 → OpenAI Responses API(含 web search)
    ├── 記憶讀取 → Supabase(回覆前撈取,與脈絡、時區並行)
    ├── reply / push 決策 → LINE Messaging API
    └── 記憶抽取 → 背景任務 → Supabase
```

| 目錄 | 內容 |
|---|---|
| [app/clients/](app/clients/) | LINE / OpenAI / Supabase 的用戶端封裝 |
| [app/repositories/](app/repositories/) | 資料存取層,一個模組對一張表 |
| [app/services/](app/services/) | 業務流程 |
| [app/prompts.py](app/prompts.py) | 角色、語氣與分寸設定 |
| [migrations/](migrations/) | 建表 SQL,依序執行 |
| [docs/DESIGN.md](docs/DESIGN.md) | 設計文件(程式碼註解引用的章節編號) |

### 技術選型

**FastAPI + Supabase + OpenAI**,與既有專案技術棧一致。

**不用 line-bot-sdk,直接用 httpx 打 REST API。** 只需要三個端點(reply / push / loading),而這個專案的成敗取決於能不能精確控制每一次呼叫的 timeout。驗簽只是 HMAC-SHA256,自己寫更好讀也好測。

**不用 supabase-py,直接打 PostgREST。** 官方套件是同步的,在事件迴圈裡呼叫會卡住整個 worker。

**對話走 Responses API,記憶抽取走 Chat Completions。** 前者可以掛 OpenAI 託管的 web search,模型判斷需要就自己查完再回答,一次往返解決;若用 function calling 自接搜尋,一題要三次往返,以本專案的時間預算根本來不及。後者用 JSON 模式,因為抽取的輸出是要被程式 parse 的。

## 記憶系統

長期記憶與短期脈絡是兩件事,少了任何一邊都會壞。

| | 長期記憶 | 短期脈絡 |
|---|---|---|
| 內容 | 抽取後的事實 | 原始對話逐字內容 |
| 用途 | 知道他是誰、在意什麼 | 聽得懂「那個」「剛剛講的」 |

以下是**虛構的**示範。使用者聊了幾句:

```
他:最近在學排氣閥的原理 說明書全英文有夠痛苦
他:而且輪機長很兇 不太敢問
他:還好有同期的同學可以抱怨 昨天靠釜山有跟他講到
```

背景抽取(累積 6 則對話才觸發,用較便宜的模型)產出:

```
[context]      使用者最近在學排氣閥的原理             重要度 4
[context]      使用者覺得全英文的說明書很痛苦         重要度 3
[relationship] 使用者覺得輪機長很兇,不太敢問他問題   重要度 4
[relationship] 使用者有同期的同學可以抱怨             重要度 3
[event]        使用者昨天靠釜山時跟同學講到學排氣閥   重要度 3
```

下次對話時這些進 system prompt,最近 20 則原始對話進 messages 陣列。於是使用者可以說一句沒有主詞的話:

```
他:那個很難欸
知平:真的,光是記那些零件英文就夠了。你哪邊卡最久?
```

**抽取時會帶著現有記憶一起問。** 不帶的話模型只會不斷產生相似記憶(「他喜歡吃泡麵」「他愛吃泡麵」「泡麵是他的最愛」);帶了 id 過去,它才能回答「更新第 3 條」而不是「新增第 4 條」。處境改變時也才知道要停用舊的而不是疊加。

模型的輸出逐項清洗:分類不合規、重要度超出範圍、內容是空的,那一項丟掉而不是整批失敗。整個 JSON 壞掉時則不標記已處理,下次連同新對話再試一次。

## 他傳什麼都要有回應

原本非文字訊息會被靜默略過。**在弱網路環境下,沒有回應會被解讀成「訊息沒送出去」**——那是最糟的處理方式。

| 傳什麼 | 處理 |
|---|---|
| 圖片 | 以 data URL 交給模型看 |
| PDF / Word / txt | 抽出文字當附註,上限 6000 字 |
| 掃描的 PDF | 抓不到文字層,建議改用拍照 |
| 舊版 `.doc` | 誠實說讀不了,並給替代做法 |
| 位置 | 更新時區(見下) |
| 貼圖 / 語音 / 影片 | 寫成一句說明交給模型,用它自己的語氣回應 |

圖片這條特別值得做:使用者的主要壓力是「要自己看全英文說明書」,拍一頁問比打字描述快得多,尤其在機艙裡手很髒的時候。實測一張手冊照片 3.7 秒、3379 input tokens。

附件內容全程只在記憶體裡,不落地成檔案——那是使用者的私人資料,少一個地方存就少一個外洩的可能。大小上限 10MB,各附件並行下載解析,避免拖垮時間預算。

**位置訊息用兩段式判斷時區**:先用地址比對已知地名(這樣拿得到正確的 IANA 時區,夏令時間規則才會對),認不出來就用經度估算(每 15 度一個時區)。後者很粗,但在公海上本來就沒有更好的答案,誤差最多一小時——總比用台灣時間跟一個在大西洋上的人說「早安」好。

## 記憶的可控性

**使用者有權知道系統記住了他什麼,並且能刪除。** 一個會記住你的系統若沒有這個開關,使用者只能選擇「全都給它」或「都不要用」。

| 指令 | 行為 |
|---|---|
| `你記得我什麼` | 依分類列出所有記憶 |
| `忘記 <關鍵字>` | 列出相符的,確認後刪除 |
| `忘記全部` | 二次確認後全部刪除 |

加好友的第一則訊息就會告知這件事,不等使用者自己發現。這是知情同意。

實作上有三個不明顯的地方,都是實機測試才發現的:

**指令辨識不能太嚴格。** 第一版要求「忘記」後面一定要有空白,結果真人打「忘記荷包蛋」完全不會被辨識,而接手的 LLM 還回「已經幫你刪掉了」——什麼都沒發生。**被告知已完成卻沒發生,比功能不存在更糟。** 現在改成比對記憶內容:句中有刪除意圖的詞,而且有記憶與這句話有夠長的共同片段。誤判在這裡是安全的,因為刪除一律二次確認。

**刪記憶不等於忘記。** 使用者當初講那句話的原始對話還在最近 20 則的脈絡裡,不處理的話它照樣講得出來。所以確認刪除後會一併遮蔽相關對話。

**指令往返不算對話內容。**「你記得我什麼」的回應是一份完整記憶清單。若存進對話紀錄,下次抽取會把整份清單重新讀成新記憶——記憶自我複製,連剛刪掉的都會復活。

## 弱網路可靠性

LINE 的回覆機制有兩種,特性完全不同:

| | Reply | Push |
|---|---|---|
| 時效 | 一次性,有效期以秒計 | 無時效 |
| 費用 | **免費** | **計入每月 200 則** |

> 一切設計以「讓 reply 成功」為目標。push 只是意外時的備援。

實測的時間分配:

```
Webhook 驗簽與回 200         5ms
loading 動畫                 立即(收到訊息當下就送,不等等待窗)
撈記憶 + 脈絡 + 時區         三個查詢並行
LLM 回覆                     閒聊 1–3s,查資料 4–5s
────────────────────────────────
從最後一則訊息算起           約 12s
```

四個機制:

**訊息合併等待窗(3 秒)。** 使用者斷線數小時後重新連上,LINE 會把累積的訊息一次送達,逐則處理會連續回覆多則。等待窗內有新訊息就重置計時,結束後合併成一次呼叫、只回一則,並用**最後一則**的 replyToken(最新的存活機率最高)。

**事件去重。** `webhook_event_id` 上的 partial unique index。刻意交給資料庫的 unique 限制而不是「先查再寫」——後者在併發下有 race condition:兩個重送幾乎同時進來,兩邊都查不到、兩邊都寫入。

**reply / push 決策。** 先試免費的 reply,失敗才在額度內改用 push。push 用量長期偏高不代表要升級方案,代表後端太慢,該回頭優化速度。

**送不出去的回覆不寫入對話紀錄。** 使用者沒看到的話不算他們的對話。若留在紀錄裡,下次組脈絡時它會以為自己講過了,開始引用對方沒讀到的內容。

## 心理邊界與生涯分寸

這是產品倫理決策,不是實作細節。

這個系統很可能成為使用者主要的傾訴管道。這是好事,但必須避免一個失敗模式——**AI 溫柔地接住了所有情緒,結果使用者因此更少向真實的人求助。**

所以情緒回應分三層:日常的累與抱怨自己接住;對自我的整體否定要先聽完、再自然地提一句家人;明顯的絕望則不自行處理,建議聯繫家人並提供求助管道。

**分層的難處在於不能誤觸發。**「累死了」「好想死喔」是中文的日常口語抱怨。沒事就跳出求助專線會很嚇人,而且會讓使用者以後不敢講真話——那等於毀掉整個系統的用途。

生涯話題則是**絕不主動開啟**。使用者主動問才認真整理選項與條件;他說「我覺得我不適合」時不要接話推薦替代方案,先聽,可以問是哪部分讓他這樣覺得。很多時候「我不適合」其實是「我學不會、沒人教」。

> 提供資訊與陪伴,不提供方向。給選項,不給建議。

## 成本控制

| 機制 | 值 |
|---|---|
| 抽取觸發門檻 | 累積 6 則對話 |
| 每日抽取上限 | 20 次 |
| 每日對話上限 | 200 則 |
| 每月 push 警戒 | 180 則(留 20 則緩衝) |
| 抽取用模型 | 較便宜的模型 |

`usage_log` 記錄每次呼叫的用途與 token 數。網路查詢單獨計次——一次查詢的 input token 約是一般對話的 **40 倍**,因為搜尋結果會整批進 context。

達到上限時的訊息**不解釋「額度」這種系統概念**——那是專案擁有者的問題,不是使用者的問題。

錯誤通知有防洪(同類一小時一次)。通知本身走 push、吃同一個額度,一個壞掉的迴圈可以在幾分鐘內把額度燒光,那時候連正常回覆都送不出去——故障通知反而造成更大的故障。

## 部署

### 環境變數

見 [.env.example](.env.example)。必要的五個:

```
LINE_CHANNEL_SECRET
LINE_CHANNEL_ACCESS_TOKEN
OPENAI_API_KEY
SUPABASE_URL
SUPABASE_SERVICE_ROLE_KEY
```

缺少必要變數時服務仍會啟動,`/health` 回 `configured: false`——這是刻意的,方便部署平台先確認容器活著,再處理設定。

### 步驟

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt

cp .env.example .env        # 填入憑證
python scripts/migrate.py   # 依序套用 migrations/
uvicorn app.main:app --reload
```

LINE Developers Console 的 Webhook URL 填 `https://<你的網址>/line/webhook`,並關閉「自動回應訊息」。本機開發用 ngrok 之類的工具開對外網址。

```bash
pytest    # 161 個測試
```

### 維運

```bash
python scripts/healthcheck.py   # 每日排程:檢查 API、資料庫、對話活躍度、備份新舊
python scripts/backup.py        # 匯出到 ~/zhiping-backups/
```

備份腳本會**拒絕**把檔案寫進專案資料夾——備份檔含完整對話紀錄,放在 repo 外是物理上不可能被 commit,比 `.gitignore` 可靠。

> 備份檔在本機仍是敏感資料。電腦送修、轉手或共用前請先處理這些檔案。

## 隱私

這個 repo 公開,但使用者的對話不公開。

- `.env`、對話匯出檔、資料庫備份一律不進版控
- README、設計文件、測試裡出現的對話**全是虛構的**
- 資料表開啟 RLS 且不建立任何 policy,只有 service role 讀得到
- 備份預設輸出到專案資料夾之外
