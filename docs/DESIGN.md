# 知平 — 設計文件

程式碼註解裡的「見 docs/DESIGN.md 5.3」指的是這份文件的章節編號。

這份文件記錄的是**為什麼這樣做**。實作細節看程式碼,這裡只寫決策與取捨。

---

## 1. 使用情境與三個限制

知平服務的是一位長期在遠洋商船上工作的使用者。所有設計決策都要回頭檢查有沒有違反這三條:

| 限制 | 影響 |
|---|---|
| 網路極差(衛星網路,常斷線) | 回應要短、要能重試、不做串流 |
| 使用者心理壓力大 | 語氣要自然不說教,不追問、不勸戒 |
| 單一使用者 | 不需要多租戶設計,但要為未來擴充留餘地 |

第三條解釋了程式碼裡幾個「這樣寫不能水平擴充」的地方——訊息合併的等待窗、待確認的刪除請求、通知防洪狀態,全都是行程內狀態。以現在的規模,換成 Redis 只是多一個會壞掉的元件。

## 2. 資料模型

四張表:`conversations`(逐字對話)、`memories`(抽取後的長期記憶)、`user_state`(時區)、`usage_log`(用量)。建表 SQL 在 [migrations/](../migrations/),每份都可重複執行。

### 2.3 時區

使用者在船上跨時區移動。若用固定時區判斷「早上」「晚上」會出錯——他半夜下班說「累死了」得到一句「早安啊」,那種細節會讓陪伴感整個垮掉。

`user_state` 存 IANA 時區字串,組 system prompt 時附上換算過的當地時間,並且加上「清晨」「深夜」這種詞:模型看到 `05:12` 不一定意識到那是什麼樣的時刻,看到「清晨」就知道對方可能剛值完夜班。

更新時區的方式**刻意不用 function calling**。那要多一次 API 往返,而「我到越南了」這種句子的變化其實很有限。改成規則判斷:要同時滿足「有地名」與「現在人在那裡」的語氣,而且不能有過去式線索。漏判只是時間講得不夠準,誤判會讓它把時間整個講錯,所以偏保守。

## 3. 記憶系統

長期記憶與短期脈絡是兩件事,少了任何一邊都會壞。

| | 長期記憶(`memories`) | 短期脈絡(`conversations`) |
|---|---|---|
| 內容 | 抽取後的事實,例如「他在學排氣閥」 | 原始對話逐字內容 |
| 用途 | 讓 AI 知道他是誰、在意什麼 | 讓 AI 聽得懂「那個」「剛剛講的」 |

只帶記憶不帶脈絡的典型失敗:使用者說「那個很難」,AI 不知道「那個」是什麼。

### 3.1 讀取

撈 `is_active = true` 的記憶,依 `importance` 降序 + `updated_at` 降序,取前 30 筆並套 1500 字上限。依 category 分組後放進 system prompt。

**記憶一律放 system prompt,不放進 user message**,避免使用者說的話被記憶內容干擾。

兩道上限都是必要的:記憶會隨時間無止盡累積,而 system prompt 的長度直接換算成每則對話的成本與延遲。

### 3.2 抽取

回覆送出**之後**才在背景跑,累積 6 則對話以上才觸發。

放在回覆路徑上會讓使用者每則訊息多等好幾秒,reply token 直接過期——那會把免費額度燒光(見第 5 節)。

抽取時**要帶著現有記憶一起問**。不帶的話模型只會不斷產生相似記憶(「他喜歡吃泡麵」「他愛吃泡麵」「泡麵是他的最愛」)。帶了 id 過去,它才能回答「更新第 3 條」而不是「新增第 4 條」。

模型的輸出不可信任,逐項清洗:category 不在四種之內、importance 不是 1–5、content 是空的,那一項就丟掉,而不是整批失敗。整個 JSON 壞掉時則不標記已處理,下次連同新對話再試一次。

抽取用較便宜的模型、JSON 模式、低溫度——這是結構化任務,不需要創造力。

一條記憶只講一件事。「他喜歡泡菜鍋,討厭苦瓜」要拆成兩條,否則使用者日後想刪掉其中一件時無從刪起。

### 3.4 可見性與可控性

使用者有權知道系統記住了他什麼,並且能刪除。這不是附加功能——一個會記住你的系統若沒有這個開關,使用者只能選擇「全都給它」或「都不要用」。

| 指令 | 行為 |
|---|---|
| `你記得我什麼` | 依 category 分組列出所有 active 記憶 |
| `忘記 <關鍵字>` | 列出相符的記憶,確認後停用 |
| `忘記全部` | 二次確認後全部停用(對話紀錄保留) |

**指令辨識的教訓**:第一版要求「忘記」後面一定要有空白,結果真人打「忘記荷包蛋」完全不會被辨識,而接手的 LLM 還回「已經幫你刪掉了」——什麼都沒發生。被告知已完成卻沒發生,比功能不存在更糟。

現在的判斷是:句中有刪除意圖的詞,**而且**有記憶與這句話有夠長的共同片段。用最長共同片段而非中文斷詞——要判斷的其實只是「使用者有沒有提到記憶裡的某個具體東西」。誤判在這裡是安全的,因為刪除一律二次確認。

**刪記憶不等於忘記**。使用者當初講那句話的原始對話還在最近 20 則的脈絡裡,不處理的話 AI 照樣講得出來。所以確認刪除後會一併遮蔽含該關鍵字的對話。

**指令往返不算對話內容**。「你記得我什麼」的回應是一份完整記憶清單,若存進對話紀錄,下次抽取會把整份清單重新讀成新記憶——記憶自我複製,連剛刪掉的都會復活。

system prompt 另外明確禁止模型宣稱自己刪除了記憶。它沒有這個能力,說了就是騙人。

### 3.5 短期脈絡

每次回覆前撈最近 20 則,依時間正序,以標準 messages 陣列帶入,總字數上限 3000 字,超過從最舊的開始捨棄。

若距離上一則對話超過 24 小時,在 system prompt 加一行標註,避免 AI 把隔了三天的對話當成剛剛才講的。

組裝順序:system prompt(角色 + 當地時間 + 記憶)→ 最近 20 則 → 本次訊息。

## 4. 成本控制

| 機制 | 值 |
|---|---|
| 抽取觸發門檻 | 累積 6 則 |
| 每日抽取上限 | 20 次 |
| 每日對話上限 | 200 則 |
| 每月 push 上限 | 180 則(留 20 則緩衝) |
| `max_tokens` | 對話 500、抽取 800 |

一次網路查詢的 input token 約是一般對話的 **40 倍**(搜尋結果會整批進 context),所以 `usage_log` 單獨記錄查詢次數。

達到每日上限時送出的訊息**不解釋「上限」「額度」這種系統概念**——那是專案擁有者的問題,不是使用者的問題。

查不到用量時一律放行:讓使用者收不到訊息的代價,大於偶爾超出幾則的代價。

## 5. 弱網路環境的可靠性

**這一節決定系統能不能用。**

### 5.1 核心限制:reply token

| | Reply | Push |
|---|---|---|
| 觸發 | webhook 帶回的 `replyToken` | 主動指定 user id |
| 時效 | 一次性,有效期以秒計 | 無時效 |
| 費用 | **免費,不計入額度** | **計入每月 200 則** |

> 一切設計以「讓 reply 成功」為目標。push 只是意外時的備援,不是常態路徑。

這代表**後端速度是成本問題,不只是體驗問題**。一個慢的實作會直接把免費額度燒光。

### 5.2 時間預算

| 階段 | 目標 |
|---|---|
| Webhook 接收與驗簽 | < 100ms(實測 5ms) |
| loading 動畫 | 立即 |
| 撈記憶與脈絡 | < 500ms(三個查詢並行) |
| LLM 回覆 | < 8s(實測閒聊 1–3s、查資料 4–5s) |
| **從最後一則訊息算起** | **約 12s** |

### 5.3 Reply / Push 決策

```
產生回覆(總體 timeout)
  → 嘗試 reply
      → 成功 → 結束
      → 失敗 → 檢查本月 push 用量
                 → 未達上限 → 改用 push
                 → 已達上限 → 記錄失敗,不再 push
```

push 用量長期偏高不代表要升級方案,代表後端太慢、reply 常常來不及——那應該回頭優化速度。

### 5.4 重複事件去重

`conversations.webhook_event_id` 上建 partial unique index,重送的事件在資料庫層被擋下。

**刻意交給資料庫的 unique 限制而不是「先查再寫」**:後者在併發下有 race condition(兩個重送幾乎同時進來,兩邊都查不到、兩邊都寫入),unique index 沒有這個問題。

### 5.5 訊息湧入的合併

使用者斷線數小時後重新連上,LINE 會把期間累積的訊息一次送達。逐則處理會連續回覆多則,體驗差也浪費額度。

作法:收到訊息先寫入資料庫,開一個 3 秒的等待窗,窗內有新訊息就重置計時。等待結束後合併成一次 LLM 呼叫,只回一則。

兩個關鍵細節:

1. 回覆用**最後一則**訊息的 replyToken——token 以秒計時效,最新的存活機率最高。
2. loading 動畫在收到訊息的當下就送出,不等等待窗結束。否則使用者會先盯著三秒的靜止畫面,那正是我們想避免的「不知道有沒有送出去」。

### 5.6 其他

- **不使用串流**:串流在衛星網路下中斷率高,對 LINE 也沒有意義。
- **外部 API 重試**:2 次指數退避,次數要納入時間預算。
- **失敗時的友善回覆**:最終失敗也要送一句簡短說明,不要讓使用者面對沉默。
- **送不出去的回覆不寫入對話紀錄**:使用者沒看到的話不算他們的對話。若留在紀錄裡,下次組脈絡時 AI 會以為自己講過了,開始引用對方沒讀到的內容。

### 5.7 驗收方式

這一節無法只靠單元測試驗證,需要實測:

- [x] 模擬後端延遲,確認 reply 失敗後正確 fallback 到 push
- [x] 連續送出 5 則訊息,確認只收到 1 則合併後的回覆
- [x] 重複送出同一 webhook event,確認不會產生重複回覆
- [x] 確認送出訊息後 1 秒內看得到 loading 動畫
- [x] 檢查 `usage_log`,確認一般對話幾乎不消耗 push 額度

## 6. 對話中的心理邊界

這個系統很可能成為使用者主要的傾訴管道。這是好事,但設計上必須避免一個失敗模式——**AI 溫柔地接住了所有情緒,結果使用者因此更少向真實的人求助。**

分三層:

| 使用者表達的內容 | 回應方式 |
|---|---|
| 日常的累、抱怨、無聊、想家 | 自己接住。陪聊、共感、轉移話題都可以 |
| 對自我的整體否定 | 先完整聽完,回應後自然地提一句有沒有跟家人講過 |
| 明顯的絕望感、提到不想活下去 | 不自行處理。溫和關心,建議聯繫家人,提供求助管道 |

**分層很重要,不要把第一層當成第三層。**「累死了」「好想死喔」是中文的日常口語抱怨,是第一層。沒事就跳出求助專線會很嚇人,而且會讓使用者以後不敢講真話——那等於毀掉整個系統的用途。

第三層**不要追問細節,也不要評估嚴重程度**。實測時模型問了「這種想法一直纏著你嗎」——那是在做評估,不是這個角色該做的事,而且被追問狀態的人會覺得像在被審問。

## 7. 專業學習與生涯支援

使用者的壓力有三層,由急到緩:當下學不會的挫折、對未來方向的迷茫、日常生活的瑣事。

**專業學習優先度最高**,因為那是當下正在發生的痛苦。而且很多時候「我不適合」的判斷其實源自「學不會、沒人教」的挫敗,不是真的不喜歡。

生涯資訊則是**被動觸發**:

| 情境 | 回應 |
|---|---|
| 主動問「還能做什麼」 | 認真整理選項,說明每條路需要什麼條件 |
| 說「我覺得我不適合」 | 不要接話推薦替代方案。先聽,可以問是哪部分讓他這樣覺得 |
| 沒提起 | **絕不主動開啟生涯話題** |

> 給選項,不給建議。

## 8. 維運

### 8.1 錯誤通知

專案擁有者不會每天檢查系統狀態,而使用者不會為了「機器人壞掉」主動抱怨。沒有通知機制,故障可能好幾週後才被發現。

OpenAI **連續**失敗 3 次才通知(單次失敗在弱網路下很常見),中間成功過就重新計數。

**防洪是必要的,不是加分項**:通知本身走 push,會吃掉每月額度。一個壞掉的迴圈可以在幾分鐘內把額度燒光——那時候連使用者的正常回覆都送不出去,故障通知反而造成了更大的故障。同類事件一小時內只通知一次。

### 8.2 健康檢查

每日一次:測 OpenAI、測 Supabase、統計當日對話數、連續 7 天沒有對話就通知。

最後一項的用意:沒有對話可能是系統壞了,也可能是使用者狀態不好或網路長期中斷。兩種情況擁有者都會想知道。所以通知內容**只陳述事實,不做任何推測**。

### 8.3 備份

> 備份檔必須存放在專案資料夾之外(預設 `~/zhiping-backups/`)。

專案資料夾是 git repo。備份檔內含使用者完整對話紀錄,屬高度敏感個資。存在 repo 內只靠 `.gitignore` 保護,一次誤操作就可能推上 GitHub;存在 repo 外則**物理上不可能被 commit**。

腳本會拒絕寫進專案資料夾底下,即使環境變數指過去。輸出檔權限設為 `600`。

超過 30 天未備份時,健康檢查會一併提醒。

### 8.4 首次啟用

加好友時送一則自我介紹,包含三點,其中第二點是**知情同意,不能省**:

> 我會記得你說過的事,你隨時可以打「你記得我什麼」來看,也可以要我忘記

一個會長期記住你的系統,使用者有權在第一時間就知道它會記住、怎麼查、怎麼刪。

## 11.1 語氣校準

語氣是最容易失敗、也最難用測試驗證的部分。預設的 LLM 語氣偏正式、偏「助理感」,不刻意壓制就會像客服機器人。

常見失敗樣態:

| 失敗樣態 | 修正方向 |
|---|---|
| 「我理解你的感受,這確實是很不容易的情況」 | 太像諮商。改成「聽起來真的很累」 |
| 每則回覆都分點列出建議 | 閒聊不需要結構化 |
| 「還有什麼我可以幫助你的嗎?」 | 客服用語,刪掉 |
| 一次回覆超過五句 | 除非是技術問題,否則太長 |

調校以修改 system prompt 為主。加入五組虛構的示範對話之後,閒聊回覆從 30–60 字收斂到 12–27 字。

**已知未解**:查資料後的回覆仍在 250–350 字之間。改了三輪 prompt(字數上限、禁止「先列點再總結」、禁止結尾追問)都只是部分改善。剩下的兩條路都不理想——調低 `max_tokens` 會在句子中間截斷,兩段式摘要要多一次 API 往返、吃掉 reply token 的餘裕。目前選擇接受:佔比 95% 的閒聊已經夠短。

**LINE 不渲染 Markdown**,而搜尋工具會照自己的慣例插入引用連結與私有區字元包住的內部標記。這些由程式統一清理,不靠模型自律——會影響使用者看到什麼的事,不該賭模型會配合。
